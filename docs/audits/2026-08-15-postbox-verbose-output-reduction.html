Pi Postbox · architecture follow-up · 2026-08-15

Spend context on decisions, not repetition.

A concrete review of the Postbox tool payloads that consumed the most model context: the 0.1.3 baseline, the smaller contracts implemented in 0.1.4, why they help, and which tempting reductions remain deliberately rejected.

What changed

The original audit mixed correctness defects with API redesign ideas. Version 0.1.3 fixed the defects and established exact evidence boundaries. With no compatibility requirement for that session-only contract, 0.1.4 implements five context reductions as the new defaults while preserving explicit full forensic views.

  "defaults": {
    "context": {
      "codebaseContext": "Postbox monorepo; audit remediation on 0.1.3.",
      "problemContext": "Choose safe changes without breaking current clients."
    }
  },
  "questions": [
    {
      "localRef": "root",
      "question": "Choose rollout strategy?",
      "options": [{"value":"staged","label":"Staged"}]
    },
    {
      "localRef": "child-a",
      "parent": {"localRef":"root"},
      "question": "Add compact detail projections?",
      "options": [{"value":"yes","label":"Yes"}]
    },
    {
      "localRef": "child-b",
      "parent": {"localRef":"root"},
      "question": "Add history event view?",
      "options": [{"value":"yes","label":"Yes"}]
    }
  ]
}
Why

Shared handoff context is often the largest repeated part of an ordered batch. One defaults object keeps the model transcript focused on the differences between decisions.

Side effects

The server performs deterministic expansion, defines complete override precedence, validates the expanded child, and persists a fully independent copy. Replay remains keyed by each item's stable request id.

Contract

docs/protocol.md → Rich context requires every persisted Question to contain nonblank codebase and problem context. Persisting a reference would violate it; server-side expansion does not.

Implemented: batch defaults.context is required; each item may provide a complete override.

Why

Most update workflows first need IDs, current ownership, status, and both revisions. A control projection avoids replaying prompts, options, and handoff context solely to obtain concurrency tokens.

Side effects

More views increase schema surface. A caller may accidentally use a compact record when it needs full content; view names should describe workflows rather than arbitrary field lists.

Contract

The 0.1.3 discovery tests deliberately required complete, untruncated details. Version 0.1.4 retains that evidence under an explicit view rather than replaying it by default.

Implemented: view:"control" is the default; request view:"full" for complete content.

Why

Long-lived Questions can repeat unchanged options and handoff context at every revision. Initial state plus typed deltas makes the actual decision history easier to inspect.

Side effects

Contract

Immutable revision evidence remains recoverable. The smaller response is derived at read time and does not replace persisted snapshots.

Implemented: event-oriented history is the default; request view:"full" for every snapshot and revision event.

04 · INPUT

Opaque concurrency shorthand

A small reduction with a large debuggability tradeoff.

do not replace defaults
Current explicit update
{
  "questionId": "ask_demo",
  "update": {
    "action": "transfer",
    "expectedRevision": 4,
    "expectedOwnerRevision": 2,
    "expectedOwner": {
      "harness": "pi",
      "ownerId": "agent-a"
    },
    "owner": {
      "harness": "pi",
      "ownerId": "agent-b"
    }
  }
}
Possible shorthand
{
  "questionId": "ask_demo",
  "ifMatch": "qv_4.2_agent-a",
  "update": {
    "action": "transfer",
    "owner": {
      "harness": "pi",
      "ownerId": "agent-b"
    }
  }
}
Why

A single token is easier to copy than two revisions plus the expected owner. Savings are modest compared with context, options, or history snapshots.

Side effects

Opaque tokens hide which dimension became stale, need versioned encoding, and can accidentally become bearer capabilities. They complicate manual repair and logs.

Spec collision

docs/protocol.md → Question update concurrency explicitly requires both revisions on every action; transfer also uses expected-owner CAS.

Recommendation: preserve explicit fields. Only add ifMatch as a transparent shorthand that returns both decoded versions in conflicts.

Stateful handle alternative
{
  "nextCursor": "cur_7Nk3pQ2m9x"

Why

A short handle costs fewer tokens and is easier to copy exactly in an agent call.

Side effects

The server now stores cursor state, enforces expiry and quotas, and must define behavior after restart. Horizontal deployments need shared state. Handles can be guessed or leaked.

Spec collision

Discovery tests require query-bound keyset cursors that remain stable when earlier Questions are inserted. Stateful handles can preserve that, but reduce deployment and restart robustness.

Recommendation: keep stateless cursors. Consider compact binary/base64url encoding before introducing server state.

06 · WORKFLOW

Assignable-owner discovery

The cost is multiple broad reads, not one oversized payload.

scoped implementation in 0.1.4
Current workflow3+ calls
1. list_questions({ scope: "global" })
   → find a Question owned by somebody else

2. get_questions({ questionIds: [...] })
   → read complete Question, options, context,
     owner, creator, revisions, timestamps

3. get_postbox_owner_status({
     owners: [{ harness: "pi", ownerId: "..." }]
   })
   → verify live / stale / offline

4. update_question({ action: "transfer", ... })

Problem: complete Question content is read only to
learn an owner identity. The result may expose unrelated
prompts and handoff context to the agent transcript.
Implemented scoped call1 discovery call
list_postbox_owners({
  scope: "feature"
})

→ [
  {
    "owner": {
      "harness": "pi",
      "ownerId": "agent-b"
    },
    "presence": "live",
    "activeQuestionCount": 0,
    "unreadAnswerCount": 0
  }
]
Why

Transfer should not require reading unrelated Question content. A compact candidate surface lowers call count and reduces accidental disclosure.

Side effects

Owner enumeration reveals limited topology and presence. The server therefore derives scope from the registered caller, forbids global discovery, and caps output at 100 owners.

Contract

Results expose no semantic state, heartbeat, session title/path, Question content, or transfer-eligibility claim. Counts are restricted to the same derived scope.

Implemented: feature by default, with caller-derived worktree or repository as the only broader choices.

Lower-volume contract cleanups

These do not dominate byte counts, but they prevent wasted calls and mistaken mutations.

Pending get_answer

Implemented in 0.1.4: return {"type":"pending","questionId":"…","status":"pending"} after the bounded read instead of the error-like “Answer not found.” Answer-read schemas and client correlation treat it as a normal union branch.

revise replacement semantics

The tool now documents that question is a complete replacement: omitted context/relevance/impact are removed. Optional options and handoff context are each preserved when omitted, but replaced completely when supplied. A future patch action should be named separately.

Scope IDs

Schema descriptions now state that repository, worktree, and feature are opaque IDs, not paths, and that callers normally set only scope. Renaming fields would be clearer but breaking; aliases can be added later.

Do not compress final Answers

The final Answer return is already concise and carries selected values, user note, rationale/status metadata, request id, and timestamp. Removing rationale would save little while discarding decision evidence the PRD explicitly values.

Design rule: reduce transport repetition without reducing persisted evidence. Expand batch defaults before storage; expose projections as explicit reads; keep complete forensic forms available; never make a shorter token less safe than the explicit state it replaces.
